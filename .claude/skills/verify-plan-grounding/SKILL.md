# verify-plan-grounding

Generate a script that asserts a plan's load-bearing claims still match code.

## When to use

- About to execute a plan from `docs/superpowers/plans/` written earlier than today
- Suspect a plan has drifted (file moved, struct renamed, line numbers shifted)
- Starting a session on a plan written by another agent or on another branch

## What this produces

A script at `scripts/verify-<plan-slug>-grounding.sh` that runs every
assertion and exits 0 on full PASS, 1 on any FAIL. Pattern matches
`scripts/verify-brain-worker-phase1-grounding.sh` — study that as the
reference implementation before generating a new one.

## Process

### Step 1 — ensure shared helpers exist

If `scripts/_verify_helpers.sh` does not exist, create it by extracting the
helper functions (`ok`, `bad`, `warn`, `section`, `assert_near`,
`assert_count`, `assert_grep`, `assert_not_grep`, `assert_file`) from
`scripts/verify-brain-worker-phase1-grounding.sh` lines ~15–80. This is a
one-time refactor — all future verify scripts source this file.

Then refactor `verify-brain-worker-phase1-grounding.sh` to source the
helpers file as well, so there's one canonical definition.

### Step 2 — read the plan

Read the full plan file. Extract every *load-bearing* claim — things the plan
asserts are true in current code that the implementation depends on:

- **File paths** the plan names (`crates/spur-core/src/orchestrator.rs`)
- **Line numbers** the plan cites (`orchestrator.rs:147`)
- **Struct / type names** the plan expects to exist
- **Function signatures** the plan expects to call or modify
- **Construction-site counts** (e.g. "there are 3 callers of `spawn_executor`")
- **Dependency versions** the plan relies on
- **Toolchain features** (rust-version floor, unstable features)
- **Config keys** in `.spur/config.toml` or `Cargo.toml`

Do NOT include aspirational claims (what the plan says it will *create*) —
only claims about current state.

### Step 3 — generate the verify script

Create `scripts/verify-<plan-slug>-grounding.sh` where `<plan-slug>` is the
plan filename without the date prefix or `.md` extension. Structure:

```bash
#!/usr/bin/env bash
# Verification script for
#   docs/superpowers/plans/<plan-filename>
# Generated by .claude/skills/verify-plan-grounding

set -u
source "$(dirname "$0")/_verify_helpers.sh"

# Group assertions by task number from the plan
section "0 · Baseline"
# toolchain checks here

section "1 · Files & deps"
assert_file "crates/spur-core/src/orchestrator.rs" "orchestrator.rs present"
# …

section "2 · <task name from plan>"
assert_near "crates/spur-core/src/orchestrator.rs" 147 'pub fn spawn_executor' "spawn_executor at cited line"
# …

# Summary
echo
echo "══ Summary ══"
echo "  PASS: $PASS  FAIL: $FAIL  WARN: $WARN"
[ "$FAIL" -eq 0 ]
```

Group checks by plan task number so stale references are easy to triage.
Use `warn` (not `bad`) for drift that doesn't block implementation.

### Step 4 — run it and report

```bash
chmod +x scripts/verify-<slug>-grounding.sh
bash scripts/verify-<slug>-grounding.sh
```

If FAIL > 0: report which claims drifted and stop. The plan needs updating
before execution.
If FAIL = 0, WARN > 0: report warnings; user decides whether to proceed.
If both 0: green-light plan execution.

## Do not

- Duplicate the helper functions inline in the generated script — always
  source `_verify_helpers.sh`.
- Assert claims about code the plan itself will create (future state).
- Generate assertions you can't verify locally (network calls, external
  services).
