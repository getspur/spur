# SIT/UAT Infrastructure Inventory

## 1. Existing harness primitives (per file)

The current testing infrastructure in `crates/spur-tui/tests/` provides a strong foundation for component-level and unit-level testing but lacks a unified integration harness for driving the `App` as a black box. Below is an inventory of the existing testing primitives and approaches used across key files.

- **`crates/spur-tui/tests/palette_integration/util.rs`**: 
  This utility module exposes `app_with_seeded_session_and_dynamic_command`, a function that constructs an `App` with a pre-seeded `SessionDetailView` and `CommandRegistry`. It ensures that tests involving the dynamic command palette stay concise. Crucially, it initializes the `App` using `App::new_for_palette_test()`, which explicitly strips away the `user_input_tx` channel and the session picker, allowing `open_palette()` to run safely in isolation. This demonstrates a pattern of isolating the `App` for specific component testing rather than full end-to-end integration.

- **`crates/spur-tui/tests/landing_paths.rs`**: 
  These integration tests verify the TUI's landing decision logic. They directly construct an `App` using `App::new_with_config(...)` and passing various `LandingDecision` variants. Instead of driving the application through the event loop, these tests assert the resulting state of the `App` structure directly. For instance, they check boolean properties like `app.dashboard_is_configured()` and verify the `app.current_view()` matches expectations (e.g., `ViewId::Dashboard`). While effective for initialization logic, this approach does not simulate user interactions.

- **`crates/spur-tui/tests/composition_intent_integration.rs`**: 
  These tests focus on the behavior of the `InputBar` component in isolation. They bypass the `App` entirely, manually instantiating an `InputBar` and driving it with raw `KeyEvent`s (e.g., `KeyEvent::new(KeyCode::Left, KeyModifiers::NONE)`). The assertions verify the internal classification of events, checking whether a specific keystroke yields an `IntentEvent::MovedCursor` or `IntentEvent::DeletedChar`. This represents a pure unit-testing strategy that is decoupled from the broader application state machine.

- **`crates/spur-tui/tests/dashboard_composer_contract.rs`**: 
  Similar to the `composition_intent_integration` tests, these regressions verify the `DashboardView` composer key-ownership contract. They instantiate a `DashboardView` directly and simulate user input using `dashboard.handle_key(...)` with a mock `ViewContext` (provided by `spur_tui::test_support::test_view_ctx`). The tests assert the returned `Option<Action>`, ensuring that keys are routed correctly based on whether the input bar is empty or non-empty. This isolates the view logic from the top-level `App` dispatcher.

- **`crates/spur-tui/tests/draft_persistence.rs`**: 
  These tests examine the persistence of draft messages across sessions. They construct an `App` (often using an internal helper `app_with_user_input_tx`) and directly call internal methods like `app.process_action(Action::SaveDraft { ... })` or manually mutate the `input_bar` text. While this verifies the interaction between the `App` state and the `SessionMetadataStore`, it circumvents the standard `handle_crossterm_event` ingestion pipeline, making it a state-mutation test rather than a behavioral simulation.

- **`crates/spur-tui/src/app.rs`**: 
  The core `App` struct exposes several `#[cfg(any(test, debug_assertions))]` helpers that hint at the beginnings of a testing harness. Methods like `handle_crossterm_event_for_test` allow pushing raw `KeyEvent`s directly into the event loop handler, while `last_action_for_test` provides a way to inspect the most recently processed `Action`. Additionally, an internal helper `app_with_user_input_tx` returns a tuple containing the `App` and the receiving end of the `UserInput` channel, enabling tests to observe outbound intents generated by the UI.

*Observation:* The existing testing infrastructure is highly modular and effectively covers the internal logic of individual components (`InputBar`, `DashboardView`, `CommandRegistry`). However, the codebase currently lacks a unified top-level test harness that allows developers to write behavioral System Integration Tests (SIT) and User Acceptance Tests (UAT) that simulate an end-to-end user journey by injecting sequences of `crossterm::event::Event`s and asserting on the resulting rendered screen buffer or outbound channel messages.

## 2. Missing primitives (recommend building)

To support a robust and ergonomic SIT/UAT testing layer that simulates user behavior accurately, the current test suite requires a dedicated abstraction that wraps the application and its dependencies. We recommend building a unified `TestHarness` structure, likely placed in `crates/spur-tui/tests/common/harness.rs`. 

The `TestHarness` should encapsulate the following core primitives:
- An instance of the `spur_tui::app::App` initialized with a test configuration.
- A `Terminal<TestBackend>` for rendering the UI to an off-screen buffer.
- A `tokio::sync::mpsc::Receiver<UserInput>` to intercept and assert on outbound actions dispatched by the TUI to the orchestrator.

**Recommended Methods for the Harness:**
To make tests declarative and readable, the harness should expose a Domain-Specific Language (DSL) or a set of ergonomic builder methods that simulate the event loop:
- `send_key(KeyCode)` and `send_key_with_mods(KeyCode, KeyModifiers)`: Wraps the boilerplate of creating a `crossterm::event::KeyEvent` and dispatching it via `App::handle_crossterm_event`.
- `type_text(&str)`: Simulates a user typing a sequence of characters by rapidly injecting multiple key events.
- `send_paste(&str)`: Constructs a `crossterm::event::Event::Paste` and feeds it directly into the application, perfectly simulating bracketed paste mechanics.
- `send_resize(u16, u16)`: Simulates terminal window resizing events to verify responsive layouts.
- `inject_backend_event(SpurEventBody)`: Simulates the orchestrator pushing an asynchronous event back into the TUI (e.g., `BrainConnected`, `AgentNotification`), effectively mocking the ACP backend without requiring a mock server.
- `take_actions() -> Vec<UserInput>`: Drains the internal `Receiver<UserInput>` channel, allowing the test to verify that the correct intents (e.g., `UserInput::Message`) were generated by the UI sequence.
- `render() -> Vec<String>`: Invokes `terminal.draw(|f| app.render(f))` to flush the UI state and then extracts the `TestBackend` buffer into an array of readable strings for assertion.
- `assert_render_snapshot(expected: &[&str])`: A convenience method that calls `render()` and compares the output line-by-line against a provided slice of strings.

Currently, developers must assemble these pieces manually, which leads to brittle tests that either bypass the main event loop (`process_action`) or fail to verify the final visual outcome. A unified `TestHarness` will bridge this gap.

## 3. ACP backend stubbing strategy

A significant challenge in UAT testing is simulating the interactions between the frontend TUI and the backend orchestrator (the `spur-core` agent runner). Fortunately, the architecture of `spur-tui` makes this remarkably straightforward. We **do not** need to build a mock server, intercept network calls, or implement complex trait-based dependency injection.

The boundary between the TUI and the backend is entirely decoupled through strict asynchronous message passing:
- **Outbound (TUI → Orchestrator)**: When a user performs an action (like submitting a message), the `App` emits a strongly-typed `UserInput` enum over an internal `tokio::sync::mpsc::Sender`. 
- **Inbound (Orchestrator → TUI)**: When the backend has an update (like streaming a new token, notifying about a spawned brain, or emitting a trace), it sends a `SpurEvent` via a broadcast receiver to the `App`'s `handle_spur_event` method.

**Strategy:**
The UAT harness will exploit this message-passing boundary. 
1. **Observing Outbound Intent**: The `TestHarness` will hold the receiving end of the `mpsc` channel. When a test scenario involves the user typing a message and pressing Enter, the test will simply assert that a `UserInput::NewSessionWithMessage` or `UserInput::Message` was received on the channel. This proves the UI successfully dispatched the user's intent.
2. **Simulating Inbound Responses**: To simulate the orchestrator processing the message and responding, the test author will construct a `SpurEventBody` directly. Because the event shapes are well-defined enums, the test can simulate complex behaviors seamlessly. For example, to simulate an agent responding, the test can inject:
   `harness.app.handle_spur_event(SpurEvent::now(SpurEventBody::BrainConnected { brain: "kiro".into() }))`
   Followed by:
   `harness.app.handle_spur_event(SpurEvent::now(SpurEventBody::AgentNotification { ... }))`

This strategy perfectly isolates the TUI state machine. It guarantees that the UATs remain fast, deterministic, and free of the flaky timing issues typically associated with spinning up real backend processes.

## 4. Snapshot vs glyph-scan vs string-contains assertions

When validating the visual state of the terminal UI, test authors have several options. Understanding the existing codebase conventions is critical for ensuring that new UATs blend seamlessly with the current test suite.

The `spur-tui` codebase explicitly avoids heavy, magical external snapshot crates like `insta`. Instead, it favors explicit, readable assertions that reside directly alongside the test logic.

- **Inline Snapshots (`&[&str]`)**: 
  Files like `crates/spur-tui/tests/session_picker_render_snapshots.rs` demonstrate the primary convention for visual assertions. They define a constant width/height, render the view to a `TestBackend`, convert the buffer to a vector of strings via `buffer_to_lines`, and assert it against an inline slice of string literals (`expected: &[&str]`). This approach is highly favored because the expected output is immediately visible in the code, and PR reviewers can easily spot structural changes in the UI directly in the diff without navigating to separate snapshot files.
  
- **Golden Files (`tests/golden/`)**: 
  For extremely complex or large visual outputs (such as the markdown rendering pipeline tested in `crates/spur-tui/tests/render_golden.rs`), the codebase uses physical `.txt` files. These tests construct `TraceEntry` values and render them, comparing the output against the `.txt` baseline. A custom script mechanism (`UPDATE_GOLDEN=1 cargo test`) handles updating these files. This is reserved for complex data that would clutter a Rust source file.

- **String-contains / Glyph-scan**: 
  For specific invariant checks where an exact layout is brittle or unnecessary, the test suite relies on substring matching or precise coordinate scanning. For example, tests for the "copy-friendly borders" feature use glyph-scanning algorithms to mathematically prove that no `│` character exists inside the selectable text bounds, regardless of the terminal dimensions.

**Recommendation for UAT Layer:**
For standard UATs and SITs, developers should use inline `&[&str]` matching against the `TestBackend` buffer. This is perfect for validating that a "Paste as atom" block renders with the correct styling and alignment. For rapid workflow validations where layout isn't the primary concern, simple `.contains()` checks on the serialized buffer string should be used. Avoid introducing `insta`, as it violates established repository patterns.

## 5. Bracketed paste injection in tests

Feature 3 requires handling large, multi-line bracketed paste events and rendering them correctly as interactive "atoms". Validating this in a UAT requires the ability to simulate the terminal's bracketed paste mode.

Fortunately, the integration is natively supported by the underlying `crossterm` library and is perfectly mapped in the `App` dispatch logic.
At `crates/spur-tui/src/app.rs:801`, the `App::handle_crossterm_event` method explicitly matches on `crossterm::event::Event::Paste(text)`. It then routes this text string down to the active view (`DashboardView`, `SessionDetailView`, or `SessionPickerView`).

In our testing harness, simulating a bracketed paste is entirely frictionless. A test author does not need to simulate the raw escape sequences (`\x1b[200~` and `\x1b[201~`) or worry about keystroke timing delays. They can simply construct the event directly:
`crossterm::event::Event::Paste("Large multiline\npaste content".to_string())`
and dispatch it through the `handle_crossterm_event` method. This faithfully replicates the behavior of a user pasting text into the terminal, ensuring that the internal parsing and eviction logic is executed exactly as it would be in production.

## 6. Vim mode test gaps

The TUI features a robust Vim emulation mode for the `InputBar`. The codebase already contains comprehensive unit tests for this functionality in `crates/spur-tui/tests/input_bar_protected_ranges.rs`. These tests rigorously verify state transitions (`EditMode::Vim(VimMode::Normal)`, `Insert`, `Visual`) and ensure that destructive commands (`d`, `c`, `y`, `p`) properly preserve immutable atom ranges.

However, a significant gap exists at the SIT/UAT level:
- **Global Event Swallowing**: The current Vim tests instantiate the `InputBar` directly. They do not verify the integration between the Vim mode and the top-level `App` event loop. In production, a user pressing `Esc` expects to transition from Insert mode to Normal mode. However, the `App` also listens for `Esc` to close overlays (like the help dialog) or cancel pending interactions. There is currently no test guaranteeing that an `Esc` keypress is routed correctly to the active view's `InputBar` rather than being swallowed preemptively by a global App-level handler.
- **Visual Feedback**: The UAT layer lacks coverage ensuring that Vim mode transitions trigger the appropriate visual UI updates. For example, switching from Insert to Normal mode should update the mode indicator in the status bar and potentially change the terminal cursor shape (e.g., from a vertical line to a block). A true UAT scenario needs to assert that these visual changes are reflected in the final render buffer.

Bridging these gaps requires driving the Vim transitions through the `TestHarness` and validating the terminal output, rather than merely checking internal enum states on an isolated component.

## 7. Performance analysis

The prompt explicitly raises performance concerns regarding a specific UAT scenario: a 60-paste eviction test simulating a user rapidly pasting text until the internal history buffers are evicted. Will generating 60 separate `Event::Paste` calls take long enough to matter (e.g., >100ms)?

The performance characteristics of the proposed SIT/UAT infrastructure are exceptionally favorable. Because the testing harness drives the application state machine entirely in-memory, it bypasses the traditional bottlenecks associated with end-to-end testing.
- **No I/O Latency**: Pushing `crossterm::event::Event::Paste` directly into the `App::handle_crossterm_event` method merely mutates internal Rust structures and sets `app.dirty = true`. It involves no actual terminal I/O, no network calls, and no thread-blocking system waits.
- **Rendering Speed**: Instructing the `TestBackend` to render the UI frame via `terminal.draw(|f| app.render(f))` is heavily optimized by `ratatui` and generally completes in 1 to 2 milliseconds.
- **Total Test Duration**: A loop injecting 60 paste events consecutively, followed by a single terminal render and assertion, will execute in less than 5 milliseconds on modern hardware.

Therefore, creating 60 separate paste events poses absolutely no performance risk to the test suite. Developers should be encouraged to write exhaustive loop-based scenarios without fear of degrading CI execution times.

## 8. Recommended layered architecture (Unit / SIT / UAT)

To maintain a healthy, comprehensible test suite, the `spur-tui` project should formalize a strict three-layer testing architecture. The current codebase occasionally conflates these layers by using complex integration setups for simple unit validations.

1. **Unit Tests (Existing)**: 
   These tests should focus exclusively on pure functions and isolated components. They instantiate components directly (e.g., `InputBar::new()`) and verify internal state mutations. They are fast, exhaustive, and should not concern themselves with the `App` or terminal rendering.
   
2. **System Integration Tests (SIT) (New)**: 
   SITs should utilize the `TestHarness` to verify the exact mapping of raw input events to outbound side-effects. They treat the `App` as a black box that accepts `crossterm::Event`s and produces `UserInput` messages. For example, an SIT might verify: `harness.send_paste("content") -> assert harness.take_actions().is_empty()` (validating that pasting does not automatically trigger a submission). SITs do not assert on the full terminal buffer, keeping them resilient to minor visual layout changes.
   
3. **User Acceptance Tests (UAT) (New)**: 
   UATs represent the highest level of behavioral testing. They simulate complete, multi-step user journeys. A UAT strings SIT primitives together into a coherent narrative: `user_pastes_error_log()` -> `hits_enter_to_submit()` -> `simulates_brain_thinking_response()` -> `assert_render_snapshot(expected_blocks)`. Crucially, UATs *must* verify the actual terminal buffer output to prove that the feature behaves exactly as the user will see it. There should generally be one UAT per major feature journey to avoid brittle over-testing.

## 9. Risks and limitations

While the proposed infrastructure is powerful, it carries a few inherent risks and limitations that developers must navigate:

- **Event Loop Decoupling**: 
  In production, the TUI operates within a continuous `tokio::select!` tick loop found in `lib.rs:run_tui_with_license`. This loop naturally interleaves crossterm events, channel receives, and rendering intervals. In our synchronized `TestHarness`, `app.handle_crossterm_event` mutates state synchronously. Tests do not perfectly mimic the concurrent nature of the real event loop. Consequently, the `app.dirty` flags must be manually flushed by the test harness; test authors must remember to call `harness.render()` explicitly to simulate the tick loop updating the screen.

- **SpurEvent Verbosity**: 
  For UAT scenarios that span complex interactions with the backend, hand-crafting `SpurEvent` objects can become extremely verbose. Constructing deeply nested `SpurEventBody::PlanUpdated` or `SpurEventBody::ExecutorReviewRequested` structs will clutter test files and reduce readability. It is highly recommended to build a `SpurEventBuilder` or a set of mock factories specifically for the UAT layer to encapsulate this verbosity, ensuring that tests remain focused on behavior rather than struct initialization boilerplate.
