1 · Entry

User types /explore in the chat input (or via the Ctrl+K universal palette). Opens the full-screen Explore view.

Open question — entry surface

A/explore + palette both open the full view← recommended
BPalette-only quick-add (no dedicated view)
CCLI only: spur explore subcommand, no TUI

2 · Browse

Three panes: sources / catalog list / preview. Preview shows the item's real frontmatter, pinned commit sha, license, and body excerpt before anything enters the pool.

Badges: in pool conflict scan ⚠ new

Open question — catalog freshness

ALive GitHub fetch when the view opens
BOffline pinned index; explicit sync refreshes← recommended (sandbox/VM-safe, deterministic)
CCache with TTL, auto-refresh in background

3 · Select

Space toggles ★. The selection is the project's polyglot pool — harness-agnostic assets SPUR will adapt to whichever worker it dispatches. It should outlive the session so teammates share the same pool.

Open question — where does the pool manifest live?

ACommitted manifest, e.g. .spur/explore.toml (source, item, pin, gate decisions)← recommended
BLocal-only state (per developer)
CNo manifest — pool lives only as installed files

4 · Security gate

This feature is the third-party ingestion path the alignment decision gated (policy W5): every item shows its pinned sha + license + scan verdict. In-the-wild research found prompt injection in ~36% of sampled public skills — the gate is not optional.

The sim shows one flagged skill and one duplicate-conflict (an ecosystem TDD skill colliding with the bundled spurpower one).

Open question — gate strictness

AHard-block flagged items, no override
BWarn + explicit override, recorded in the manifest← recommended
CWarn only, install proceeds

5 · Apply

Apply only vendors the pinned bodies into the pool and writes the manifest. No harness fanout happens here — that's the point of the polyglot model: materialization is owned by orchestration, not by install.

Open question — how are bodies stored?

AVendor full bodies into the repo (reviewable diffs, reproducible, offline dispatch)← recommended
BManifest-only; fetch at dispatch time
CGit submodules per source repo

6 · Orchestrate (the core)

Skills/personas are managed on the fly: when the brain delegates, plans, or loops, SPUR renders the relevant pool subset into the worker's harness-native location (worktree-scoped), and personas become dispatchable targets.

Open question — where does materialization land?

AEphemeral: rendered into the worker's worktree at dispatch, never committed← recommended (pure on-the-fly)
BCommitted repo fanout (like bundled spurpower skills)
CHybrid: bundled spurpower committed, explored pool ephemeral

Open question — which pool subset per dispatch?

AEverything in the pool, every dispatch
BBrain picks a task-relevant subset per delegation (context economy)← recommended
CWorker pulls on demand mid-run (needs harness support)

7 · Manage

Pool lifecycle: drift vs upstream, updates re-enter the gate, removal cleans vendored bodies. The “Last materialization” lens answers “what did my codex worker actually load on the last dispatch?”.

Open question — drift checking

AManual sync + badge in the TUI← recommended
BAuto-check on TUI start
CScheduled job opens an update PR
